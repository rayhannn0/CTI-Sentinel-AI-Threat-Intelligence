# Lab 9 — MongoDB Write Concerns and Network Partitions

## Clean, separate lab cluster

This project uses `lab9_isolated` Docker Compose, MongoDB 7.0, 3 data-bearing voting members, ports `27317` / `27318` / `27319` and DB `lab9`. It does not touch the Lab 8 containers and has no fixed container names. Docker Desktop must be running. Avoid `docker compose down -v` because it deletes lab data.

The data are generated by live runs. The activity JSON files are reproducible examples and output schemas, not invented benchmark results.

## Mac Terminal quick start (from the extracted project directory)

```bash
python3 -m pip install -r requirements.txt
python3 verify_project.py
python3 bootstrap.py
python3 run_all.py
```

This runs Lab 9.1 (1000 inserts per concern) and Activity 9.1 (j=true and j=false combinations). The first Docker image build can take longer. Results are in `output/lab_9_1.json` and `output/activity_9_1.json`.

## Network partition — intentional, must be separate

Keep Docker Desktop running and only run this on the disposable Lab 9 replica set. It disconnects SECONDARIES on the isolated Docker network; it automatically reconnects them in a `finally` block, but a hard power loss or process kill can prevent cleanup.

```bash
python3 partition_controller.py
```

Monitor in another Terminal during the experiment:

```bash
docker compose --profile runner run --rm labrunner python 03_Lab_9_2/lab_9_2.py --seconds 75
```

After recovery, record statuses from inside the Docker network:

```bash
docker compose --profile runner run --rm labrunner python 04_Activity_9_2_Try_It_Yourself/activity_9_2.py
```

If Docker's secondary stays disconnected due to a crash, check `docker network inspect lab9_isolated_lab9net` and reconnect the specific container using `docker network connect --alias mongo2 lab9_isolated_lab9net <container_id> (use --alias mongo3 for mongo3)`. Do not delete volumes.

## Important notes

- `w=3` means all three **data-bearing** nodes in this separate replica set. An arbiter never acknowledges a write.
- `w:1` will usually be faster, but neither speed ratios nor election timing are guaranteed.
- When just one secondary is isolated, primary + remaining secondary still form a majority, so majority writes are normally acknowledged.
- When both secondaries are isolated, the former primary typically steps down; both w=1 and w=majority may fail because there may be no writable primary. Do not promise a w=majority timeout on every run.
- MongoDB 7.x journaling and majority acknowledgment are affected by server settings. Measurements are environment specific.
